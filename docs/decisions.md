# Decisions

## D-001 — Python standard library for the first slice

Первое ядро использует Python 3.11 и стандартный `unittest`. Это делает расчёты
воспроизводимыми без установки инфраструктуры и не мешает позднее подключить
FastAPI/PostgreSQL после решения по Phase 0.

## D-002 — JSON Golden Dataset

Исходные данные Phase 0 хранятся в нескольких читаемых JSON-файлах. Business
logic не зависит от формата: loader отделён от доменных расчётов. Это позволяет
перенести сущности в PostgreSQL без переписывания TCO calculator.

## D-003 — Integer RUB amounts

Тестовые цены хранятся целыми рублями. Float для денег не используется. Если
источники потребуют копейки, модель будет мигрирована на integer kopecks без
изменения алгоритма.

## D-004 — Explicit consumable channels

У продукта явно перечислены обязательные каналы расходников, например `black`
или `cyan`. Каждая связь с расходником также задаёт применимость к страницам:
`mono_pages`, `color_pages` или `all_pages`. Движок не угадывает расход чернил
по типу печати и обнаруживает отсутствующий канал как неполные критичные данные.

## D-005 — One canonical OEM replacement per channel in Phase 0

Для каждого канала Golden Dataset выбирает один явно обоснованный OEM replacement
package. Оптимизация комбинаций standard/high-yield упаковок пока не реализуется:
она может скрыть ошибки данных и не нужна для проверки базовой гипотезы. Выбор
канонического расходника должен быть объяснён evidence/notes.

## D-006 — Explicit page-equivalent weights

Некоторые maintenance items имеют разный ресурс при монохромной и цветной
печати. Например, опубликованные 16 000 mono / 4 000 color pages означают, что
одна цветная страница расходует четыре эквивалентные единицы ресурса. Связь
product–consumable хранит явные `mono_page_weight` и `color_page_weight`; движок
не выводит их из технологии или названия расходника.

## D-007 — Maintenance completeness is explicit

Отсутствие maintenance link само по себе неоднозначно: отдельного элемента может
не быть, либо его просто не исследовали. Поэтому у продукта есть проверяемый
`maintenance_data_status`. Значение `incomplete` блокирует TCO, а
`not_published` сохраняется как предупреждение.

## D-008 — Conflicts remain visible

Наличие одного выбранного `verified` факта не удаляет противоречащий источник.
Конфликт сохраняется как отдельный `Evidence` со статусом `conflict` и попадает
в аудит полноты. Это позволяет считать по более приоритетному источнику, не
создавая ложного впечатления, что исходные данные однозначны.

## D-009 — Промежуточная рекомендация не равна Phase 0 gate

До достижения 30 моделей отчёт может выдать процессную рекомендацию
`CONTINUE PHASE 0`, только если все заданные сценарии имеют хотя бы две
рассчитываемые альтернативы, есть хотя бы одна смена победителя относительно
цены покупки и контроль чувствительности даёт не менее двух разных победителей.
Это означает лишь наличие раннего сигнала для продолжения сбора данных.
Итоговый `GO`, `REASSESS` или `NO-GO` по этой рекомендации не выставляется.

После достижения минимальных 30 моделей gate формируется кодом. Отсутствие смен
относительно purchase-price baseline означает `NO-GO`; наличие экономического
эффекта при недостаточной чувствительности к объёму означает `REASSESS`; `GO`
возможен только при полном сценарном покрытии, сменах победителя и как минимум
двух победителях в контрольных точках объёма. Это проектное правило Phase 0, а
не отраслевой стандарт.

## D-010 — Primary price and observed market range

Для детерминированного headline TCO у каждой сущности остаётся одно выбранное
`primary`-наблюдение цены. Другие проверенные предложения хранятся рядом как
неосновные наблюдения и используются для консервативной проверки устойчивости:
верхняя граница TCO текущего победителя сравнивается с нижней границей TCO
остальных кандидатов. Это не заменяет price feed, но обнаруживает рекомендации,
которые могут измениться от выбора магазина.

## D-011 — Installed maintenance yield may differ from replacement yield

Если комплектный maintenance item имеет ресурс, отличный от сменной детали,
связь product–consumable хранит явный `installed_yield_value`. После исчерпания
установленного ресурса каждая покупаемая сменная единица использует обычный
`Consumable.yield_value`. Значение добавляется только по опубликованному
источнику и не выводится из названия детали.

## D-012 — Число моделей не равно числу независимых TCO-конфигураций

Отчёт отдельно считает уникальные конфигурации стартовых, сменных и maintenance
расходников. Для starter сравнивается фактический суммарный ресурс, а не
модельно-специфичный ID. Так семейные варианты с одинаковой экономикой не
раздувают разнообразие Golden Dataset, хотя остаются отдельными продуктами для
проверки цены и hard constraints.

## D-013 — Двумерная чувствительность не должна подменяться стартовым комплектом

Контроль «доля цветной печати × горизонт владения» использует фиксированные
750 страниц в месяц, доли цвета 0/25/50/75% и горизонты 1/3/5 лет. Предварительная
сетка на 200 страницах в месяц была отвергнута: стартовых чернил Canon G1411 и
HP Smart Tank 580 хватало почти на весь тест, поэтому он измерял в основном цену
устройства, а не экономику владения.

Сетка считается отдельно без функциональных требований и с обязательными МФУ +
Wi-Fi. Переключение победителя только между этими профилями не считается
чувствительностью экономики: оно может быть целиком вызвано hard constraints.
Контроль остаётся диагностикой и не ослабляет Phase 0 gate из D-009.

## D-014 — Retailer basket fails closed

Проверка цены одного продавца отделена от обычных `PriceObservation`. Корзина
считается полной только если точные устройства и все выбранные OEM replacement
consumables подтверждены как находящиеся в наличии у одного продавца на одну
дату. Ожидаемые, транзитные, недоступные и неподтверждённые позиции не дают
права рассчитывать basket-aware TCO.

Неполные корзины сохраняются как аудит покрытия источника, но не меняют primary
цены и ranking. Это fail-closed правило не позволяет незаметно собрать красивый
результат из минимальных цен разных магазинов или архивных карточек.

## D-015 — Full-TCO ablation is an accounting identity

Вклад полного расчёта раскладывается воспроизводимо:

```text
full_tco = simplified_tco - starter_credit + maintenance_cost
```

`starter_credit` — разница обязательных покупок replacement consumables между
упрощённым и полным расчётом с учётом целых упаковок. Отчёт проверяет identity
кодом и показывает обе составляющие для каждого сценария, где меняется
победитель. Это отделяет реальную пользу starter/maintenance от обычного
сравнения стоимости сменных расходников.
