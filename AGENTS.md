# AGENTS.md — Product Decision Engine

## 0. Назначение этого файла

Этот файл содержит постоянные правила проекта и техническое задание на **Phase 0 — Proof of Value**.

Codex должен читать его как проектный контракт. Если пользователь даёт более новое явное указание, оно имеет приоритет, но Codex не должен молча менять цели проекта, архитектурные принципы или расширять scope.

Рабочее название проекта: **Product Decision Engine**.

Язык общения с владельцем проекта: **русский**.
Имена сущностей, файлов, таблиц, функций и классов в коде: **английский**.

---

# 1. Миссия проекта

Создать российский web-first сервис, который помогает человеку выбрать товар не по минимальной цене покупки, а по **реальной экономической выгоде под его сценарий использования**.

Ключевой вопрос сервиса:

> «Что мне выгоднее купить именно при моём способе использования и горизонте владения?»

Сервис должен со временем поддерживать несколько товарных категорий через общее ядро и специализированные расчётные модули.

Первая тестовая категория: **домашние и малые офисные A4-принтеры/МФУ**.

Будущие вероятные категории могут включать смартфоны с longevity/TCO, роботы-пылесосы, кофемашины и другие товары, но **Phase 0 не должна реализовывать их**.

---

# 2. Главная продуктовая гипотеза

Мы должны доказать, что специализированный Decision Engine даёт человеку полезный результат, который заметно лучше простой сортировки товаров по цене покупки.

Для принтеров это означает:

- более дешёвый при покупке принтер не обязательно дешевле во владении;
- оптимальный выбор может меняться при изменении месячного объёма печати;
- оптимальный выбор может меняться при изменении доли цветной печати;
- более дорогой принтер может окупиться за счёт дешёвых расходников;
- рекомендованный месячный объём и обязательные функции должны ограничивать выбор до расчёта TCO;
- каждая существенная цифра должна быть воспроизводима и иметь источник.

Если Phase 0 не подтверждает эту гипотезу на реальных данных, проект необходимо остановить или пересмотреть до разработки полноценного сайта.

# 3. Основные архитектурные принципы

## 3.1. Facts live in data, not in the LLM

LLM не является источником истины.

Факты вроде:

- ресурс картриджа;
- стартовый ресурс;
- совместимость;
- рекомендуемая нагрузка;
- цена;
- модель расходника;

должны храниться в БД/тестовом dataset вместе с источником.

LLM не должна самостоятельно создавать `verified` факт.

---

## 3.2. Deterministic calculations

TCO, фильтрация, ranking, break-even и другие числовые результаты должны вычисляться обычным детерминированным кодом.

Запрещено просить LLM «примерно посчитать TCO» и использовать её ответ как продуктовый результат.

Одинаковые входные данные должны давать одинаковый расчёт.

---

## 3.3. Evidence-first

Каждый внешний факт, влияющий на рекомендацию, должен иметь provenance/evidence.

Минимально для факта должны быть известны:

- источник;
- URL или иной идентификатор источника;
- дата получения/проверки;
- тип источника;
- статус доверия.

При конфликте источников более авторитетный источник имеет приоритет, а конфликт должен быть обнаружим.

Предпочтительный приоритет:

1. производитель / официальный datasheet;
2. официальный API/feed/brand-authorized catalog;
3. надёжный структурированный каталог;
4. несколько независимых retailers;
5. LLM/web inference — только как кандидат на проверку, не как verified fact.

---

## 3.4. High precision over maximum coverage

Лучше не рекомендовать товар из-за неполных данных, чем уверенно рассчитать неправильный TCO.

Если обязательного факта нет, система должна:

- исключить модель из конкретного расчёта;
- или явно пометить расчёт как неполный;
- но не придумывать значение.

---

## 3.5. Collect broadly, enrich narrowly

В будущем проект может импортировать базовые сведения о большем числе товаров и категорий, если это разрешено источником.

Однако глубокое enrichment, ручная проверка, LLM-обработка и специализированные метрики выполняются только для текущей поддерживаемой категории.

`unsupported` не означает `delete`.

Но Phase 0 не должна тратить время на глубокую обработку A3, плоттеров, этикеточных, профессиональных фотопринтеров и других будущих категорий.

---

## 3.6. Provider abstraction

Проект не должен быть намертво привязан к одному внешнему поставщику данных или AI.

В будущем ожидаются интерфейсы уровня:

- `PriceProvider`
- `CatalogProvider`
- `AIProvider`
- `EvidenceProvider`

Phase 0 не обязана реализовывать все эти адаптеры, но код не должен специально проектироваться так, будто один внешний сайт будет вечным единственным источником.

---

## 3.7. No premature complexity

Запрещено без необходимости добавлять:

- Kubernetes;
- Kafka;
- Airflow;
- микросервисную архитектуру;
- Redis «на будущее»;
- отдельный vector database;
- event bus;
- собственную большую LLM;
- сложную auth-систему;
- мобильное приложение;
- Telegram-бот.

Сначала доказать ценность ядра.

# 5. Phase 0 — Proof of Value

## 5.1. Цель

Построить небольшой воспроизводимый прототип Printer Decision Engine и доказать на реальных данных, что он способен выбирать принтеры полезнее, чем простая сортировка по цене покупки.

Главный результат Phase 0 — не UI, а работающий и протестированный расчётный движок с Golden Dataset.

---

## 5.2. Объём Golden Dataset

Цель: **30–50 реальных моделей** принтеров/МФУ.

Нужна разнообразная выборка:

- монохромные лазерные;
- цветные лазерные;
- струйные картриджные;
- струйные с ёмкостями/СНПЧ;
- принтеры;
- МФУ;
- несколько производителей.

Желательные бренды для первой выборки:

- Pantum;
- Brother;
- HP;
- Canon;
- Epson;
- при удобстве данных — Kyocera, Xerox, Lexmark.

Не требуется идеальное равномерное распределение.

Главный критерий — разнообразие моделей расходников и поведения TCO.

---

## 5.3. Источники данных Phase 0

Для Proof of Value допустим ручной сбор небольшого test dataset из публично доступных страниц и официальных datasheet.

Цены в Phase 0 можно внести вручную как **test observations**.

Мы НЕ считаем этот dataset коммерческой production-базой.

Для каждого критического технического факта предпочтителен официальный источник производителя.

Минимум:

- model/manufacturer;
- device type;
- mono/color capability;
- printer/MFP;
- Wi-Fi;
- automatic duplex, если применимо;
- recommended monthly volume, если опубликован;
- starter consumables;
- starter yield;
- replacement OEM consumables;
- replacement yield;
- required maintenance item и его yield, если это существенно для рассматриваемого горизонта и данные доступны;
- test current device price;
- test current OEM consumable price;
- evidence for every TCO-critical fact.

# 6. Минимальная предметная модель

Не усложнять без необходимости.

Рекомендуемый минимальный набор сущностей:

## `Consumable`

# 7. Модель пользовательского сценария

Минимальный `UsageScenario`:

- `mono_pages_per_month`
- `color_pages_per_month`
- `ownership_months` или `ownership_years`
- `max_purchase_price_rub` nullable
- `require_mfp`
- `require_wifi`
- `require_auto_duplex`

Дополнительные параметры добавлять только если они реально нужны для сценариев Phase 0.

Не создавать «универсальный опросник на 40 вопросов».

---

# 8. Фильтрация до ranking

Сначала проверить hard constraints пользователя.

Например:

- нужен цвет → mono-only исключается;
- нужен MFP → printer-only исключается;
- нужен Wi-Fi → устройства без Wi-Fi исключаются;
- нужен auto duplex → неподходящие исключаются;
- месячная нагрузка заметно превышает явно опубликованную рекомендуемую нагрузку → модель не должна занимать первое место только из-за низкого TCO.

После hard constraints считать экономику.

`recommendation score` не должен быть просто смесью десятков выдуманных коэффициентов.

В Phase 0 основной ranking после соответствия требованиям = **минимальные подтверждённые обязательные расходы за выбранный период**.

---

# 9. Базовая математика TCO

Расчёт должен быть явным и покрыт тестами.

## 9.1. Объём печати

```text
mono_pages_total = mono_pages_per_month * ownership_months
color_pages_total = color_pages_per_month * ownership_months
```

Для цветной печати учитывать реальную модель расхода конкретной технологии. Не предполагать автоматически, что все устройства используют расходники одинаково.

---

## 9.2. Starter consumables

Расходники из комплекта уменьшают объём, который надо покрыть сменными расходниками.

Нельзя путать starter yield и replacement yield.

---

## 9.3. Покупаются целые единицы

Если человеку нужно 1100 страниц после стартового расходника, а сменный картридж рассчитан на 3000 страниц, фактические денежные расходы включают покупку одного полного картриджа.

Использовать целочисленный расчёт количества покупок там, где это соответствует реальности.

---

## 9.4. Maintenance items

Если производитель публикует отдельный drum/imaging unit/maintenance box и по сценарию его ресурс будет исчерпан, стоимость должна учитываться.

Если данных недостаточно — не придумывать.

---

## 9.5. Не учитывать пока

В headline TCO Phase 0 не включать без необходимости:

- бумагу;
- электричество;
- ремонт;
- стоимость времени пользователя;
- resale value;
- инфляционный прогноз;
- неоригинальные расходники;
- заправку;
- «среднюю надёжность из интернета».

---

# 10. Break-even

Phase 0 должна проверить возможность рассчитать экономический break-even между двумя моделями.

Пример вопроса:

> «При каком месячном объёме более дорогой Epson становится выгоднее дешёвого Canon на горизонте 5 лет?»

Алгоритм может быть численным перебором разумного диапазона объёмов печати.

Не требуется выводить закрытую математическую формулу, если простой детерминированный поиск надёжен и понятен.

---

# 11. Baselines для эксперимента

Для каждого тестового сценария сравнивать минимум три подхода.

## Baseline A — Purchase Price

Среди моделей, удовлетворяющих hard constraints:

```text
ORDER BY purchase_price ASC
```

## Baseline B — Simplified TCO

Цена устройства + основные расходники без полной модели starter/maintenance, если нужен отдельный baseline.

## Candidate — Decision Engine

Полный расчёт Phase 0.

Цель — измерить, насколько часто и насколько существенно Candidate меняет решение относительно Baseline A.

---

# 12. Набор тестовых пользовательских сценариев

Создать минимум **10–15 сценариев**, охватывающих разные профили.

Примеры:

1. Очень редкая домашняя ч/б печать.
2. Домашняя печать + немного цвета.
3. Студент, умеренная печать документов.
4. Учитель, высокий объём ч/б + цвет.
5. Малый офис, высокая монохромная нагрузка.
6. Домашнее МФУ с Wi-Fi обязательно.
7. Сценарий с обязательным дуплексом.
8. Низкий бюджет покупки, длинный горизонт владения.
9. Высокий бюджет покупки, приоритет минимального TCO.
10. Сценарий, где нагрузка должна исключить слишком слабую модель.

Не подгонять сценарии специально под доказательство гипотезы.

Они должны выглядеть как реалистичные пользовательские ситуации.

# 13. Основные метрики Phase 0

Нужно получить измеримые результаты.

Минимум:

## 13.1. Recommendation Change Rate

Доля сценариев, где лучший по Decision Engine товар отличается от самого дешёвого подходящего по purchase price.

## 13.2. Economic Impact

Для каждого сценария:

```text
purchase_price_winner_tco - decision_engine_winner_tco
```

Показывает потенциальную экономию относительно наивного выбора.

## 13.3. Ranking Sensitivity

Проверить, меняется ли победитель при изменении объёма использования.

Например:

- 50 pages/month;
- 200;
- 500;
- 1000.

## 13.4. Explainability Coverage

100% рекомендаций должны раскладываться на понятные компоненты:

- purchase cost;
- consumables;
- maintenance;
- количества купленных единиц;
- использованные yields;
- evidence.

## 13.5. Data Completeness

Для каждой модели показать, каких обязательных данных не хватает.

# 14. Критерии GO / NO-GO после Phase 0

Это проектные критерии, а не отраслевой стандарт.

## GO, если одновременно выполняется следующее

1. Движок стабильно и воспроизводимо считает TCO на Golden Dataset.
2. Каждая существенная цифра имеет evidence.
3. Для заметной части реалистичных сценариев лучший TCO-выбор отличается от простого выбора самого дешёвого устройства.
4. В нескольких сценариях экономический эффект достаточно велик, чтобы пользователь реально мог изменить решение о покупке.
5. Результат чувствителен к сценарию использования: один и тот же winner не побеждает бессмысленно почти везде.
6. Можно объяснить рекомендацию простыми цифрами без магического AI score.
7. Нет необходимости в данных, которые практически невозможно получать даже вручную для тестовой выборки.

## NO-GO / REASSESS, если

- почти всегда выигрывает самый дешёвый подходящий принтер;
- отличие TCO обычно несущественно;
- ranking чрезмерно зависит от непроверяемых предположений;
- большая часть моделей требует ручных догадок о расходниках;
- результат нельзя объяснить пользователю;
- модель данных пришлось сделать чрезмерно сложной уже на 30–50 устройствах;
- расчёты регулярно требуют LLM-галлюцинаций вместо фактов.

Не скрывать отрицательный результат Phase 0. Цель Phase 0 — проверить гипотезу, а не любой ценой доказать её.

---

# 15. Тестирование

Обязательны автоматические тесты на денежные расчёты.

Минимум проверить:

- starter yield полностью покрывает usage;
- usage ровно равен replacement yield;
- usage на 1 страницу больше yield → требуется следующая целая единица;
- отсутствие color consumable;
- отдельный drum достигает ресурса;
- drum не достигает ресурса;
- hard constraint исключает дешёвую, но неподходящую модель;
- zero pages scenario;
- 1 month / 1 year / 5 years;
- missing critical data;
- conflicting data handling, если реализовано.

Денежные значения не хранить во float без необходимости. Использовать безопасное представление для валюты.

## При неоднозначности

Если можно выбрать простое и сложное решение, предпочитать простое, если оно не блокирует цель Phase 0.

## При обнаружении новой идеи

Записать в backlog или сообщить владельцу проекта.

## При обнаружении ошибки в исходных данных

Не исправлять её «по смыслу» без evidence.

## При написании кода

- избегать магических чисел;

- отделять business logic от I/O;
- держать TCO calculator чистым и тестируемым;
- не смешивать scraping/import code с расчётным ядром;
- новые внешние зависимости добавлять только при понятной пользе.

# 19. Data/legal guardrails на текущем этапе

Phase 0 является исследовательским прототипом.

Допустимо вручную собирать небольшое количество публично доступных фактов и тестовых цен для Golden Dataset.

При переходе к массовому автоматическому сбору и коммерческому production необходимо отдельно проверять:

- условия API/feed;
- права на хранение и повторное использование данных;
- Terms of Service источника;
- ограничения на автоматический доступ;
- требования к атрибуции;
- возможность коммерческого использования.

Не проектировать production так, чтобы он требовал постоянного обхода CAPTCHA, rate limits или иных технических ограничений чужого сервиса.

Но не блокировать Phase 0 из-за отсутствия production-договора на price feed: тестовые цены можно внести вручную.

# 20. Что считается завершением Phase 0

Phase 0 завершена только когда существует воспроизводимый отчёт, построенный кодом, а не вручную.

Минимальный deliverable:

1. Golden Dataset из 30–50 реальных моделей.
2. Evidence для TCO-critical facts.
3. 10–15 UsageScenario.
4. Рабочий deterministic TCO calculator.
5. Hard-constraint filtering.
6. Ranking по TCO.
7. Break-even хотя бы для выбранных пар моделей.
8. Automated tests.
9. Скрипт/команда оценки всех сценариев.
10. Отчёт с:
   - purchase-price winner;
   - Decision Engine winner;
   - TCO обоих;
   - экономической разницей;
   - причинами выбора;
   - источниками;
   - aggregate metrics Phase 0.
11. Явный вывод: `GO`, `REASSESS` или `NO-GO` с аргументами.

# 22. После Phase 0 — НЕ реализовывать без отдельного решения

Если Phase 0 = GO, следующий этап обсуждается отдельно.

Вероятная последовательность:

1. Data Engine / PostgreSQL.
2. Automated importers and normalization.
3. Real price providers.
4. Public web MVP.
5. Analytics and monetization experiment.
6. LLM conversational/explanation layer.
7. Smartphone Longevity + TCO category gate.
8. Price/history enhancements.
9. Telegram Decision Watch — следить не только за ценой конкретного товара, а за изменением оптимального решения под сохранённый пользовательский сценарий.

Codex не должен перепрыгивать к этим этапам сам.

# 23. Ключевые правила проекта — короткая версия

Если Codex должен запомнить только несколько вещей, это они:

1. **Мы строим Decision Engine, а не каталог и не AI-wrapper.**
2. **Сначала доказать ценность на 30–50 принтерах.**
3. **LLM не является источником фактов и не считает TCO.**
4. **Каждая существенная цифра должна иметь evidence.**
5. **Лучше отказ от расчёта, чем уверенно неправильный результат.**
6. **Сначала hard constraints, потом экономика.**
7. **Сравнивать Decision Engine с наивным выбором по purchase price.**
8. **Не расширять scope Phase 0 без явного разрешения.**
9. **Не усложнять инфраструктуру заранее.**
10. **Отрицательный результат Phase 0 допустим и полезен.**
